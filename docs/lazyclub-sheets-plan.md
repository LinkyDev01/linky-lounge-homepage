# 커피앤바 + 레이지클럽 신청 스프레드시트 분리 — 실행 계획 (2026-08-24)

> 운영자 지시 4건의 실행 설계. **결정 대기 항목이 해소되는 대로 단계별 착수.**
> 관련 규율: CLAUDE.md §6(GAS 계약)·§4(공유 데이터 지도) · `docs/gas-automation.md`

## 0. 지시 원문 요지

1. 안동민·천고든 소개의 **네비올로 / 네그로니 링크** → '동민과 고든 커피앤바' 참가폼으로
2. 그 페이지 **우상단 원형 로고를 10초 반시계 회전**
3. 접수는 **북클럽과 다른 스프레드시트 파일**로. 겸사겸사 **레이지클럽 전용 시트 신설,
   모임 단위로 탭 관리**
4. **원데이토크 도착지도 레이지클럽 시트로 이전** + 한 칼럼에 뭉친 정보를 **항목별 분해**

## 1. 현재 구조 (실사 결과)

| 항목 | 현재 |
|---|---|
| GAS 정본 | `gas/linkyincdev-main.gs` (main 병합 시 자동 배포) |
| 시트 바인딩 | **`SHEET_ID` 단 하나** — 북클럽 시트(`1yDy7…`) 고정, `ss()` 가 전역 사용 |
| 원데이 접수 | `handleOnedayApply` → `'1회성 모임'` 탭 (같은 문서 안 별도 탭) |
| 프론트 → GAS | `/api/lazyday/apply` → `INTERVIEW_GAS_URL` 프록시 |
| 원데이 payload | `type:"oneday"` + name/gender/age/phone/greeting/instagram/**meetingDates**/orderId/marketingConsent/consentAt |

**칼럼 뭉침의 원인**: 프론트가 제목·회차·일시를 **하나의 문자열**로 합쳐 `meetingDates`
한 필드에 보낸다(`MeetingApplyForm.tsx`). GAS 는 그걸 '모임 일자' 한 칸에 그대로 적는다.
→ **분해는 시트가 아니라 payload 구조화가 선행**이다.

## 2. 목표 구조

```
레이지클럽 신청 관리 (신규 스프레드시트, 별도 파일)
├─ 커피앤바            ← 신규
├─ 원데이 토크          ← 북클럽 시트에서 이전
└─ (모임 늘면 탭 추가)
```

- GAS 는 `SHEET_ID`(북클럽) 옆에 **`LAZYCLUB_SHEET_ID`** 를 두고, 레이지클럽 계열
  핸들러만 그쪽을 본다. 기존 북클럽 핸들러는 **한 줄도 건드리지 않는다.**
- 탭 이름은 모임 단위. 모임이 늘면 **payload 의 slug 로 탭을 자동 생성**(`ensureSheet`)
  — 모임 추가할 때마다 GAS 를 고치지 않아도 되게.

### 원데이 토크 칼럼 분해 (현행 → 목표)

| 현행 | 목표 |

| 주문번호 | 그대로 (payUrl 여정은 공란 — §4) |
| 한 줄 인사·인스타그램·마케팅 동의·동의 시각 | 그대로 |

## 3. 실행 순서 (§6 절차 — GAS 먼저, 프론트 나중)

**A. 커피앤바 페이지** (프론트 단독, 시트와 독립)
- `/lazyclub/meetings/coffee-and-bar`(슬러그 확정 필요) 신규 페이지
- 운영자 카피 원문 그대로. 참가비 2만원/시간 · 환영 음료 · 신청서 5필드
  (이름·나이·전화번호·자기소개·희망 날짜와 시간대)
- 우상단 원형 로고 10초 반시계 회전 (`animation: spin 10s linear infinite reverse`,
  `prefers-reduced-motion` 정지)
- 사람 소개의 네비올로·네그로니 `<a>` 목적지 교체 (people-config)

**B. 레이지클럽 시트 신설 + GAS 라우팅**
1. 새 스프레드시트 생성 → ID 확보 (**생성 주체 결정 필요**)
2. GAS: `LAZYCLUB_SHEET_ID` + `lazyclubSs()` 추가, `ensureSheet(탭)` 헬퍼
3. `handleCoffeeBar` 신설 (`type:"coffeebar"`) → '커피앤바' 탭
4. main 병합 → **GAS 새 버전 배포 확인** → 그 다음에 프론트 폼 병합

**C. 원데이 토크 이전 + 칼럼 분해**
1. 프론트: payload 를 구조화 (`meetingTitle`·`meetingSlug`·`meetingDate`·`sessions`)
   — **`meetingDates` 는 당분간 함께 보낸다**(구 GAS 가 살아 있어도 안 깨지게)
2. GAS: `handleOnedayApply` 가 새 필드를 우선 쓰고 없으면 `meetingDates` 폴백,
   기록 대상을 레이지클럽 시트의 '원데이 토크' 탭으로
3. 배포 확인 후 프론트 병합 → 실제 접수 1건으로 검증 → 안정되면 `meetingDates` 제거

## 4. 위험과 대비

- ⚠ **뒤집힘 유실**: 프론트가 먼저 나가면 새 필드를 구 GAS 가 몰라 조용히 사라진다
  (§6 규칙). 반드시 **GAS 새 버전 확인 후 프론트 병합**.
- ⚠ **기존 접수 흐름 무중단**: 북클럽 핸들러·`SHEET_ID` 불변. 레이지클럽은 새 상수로만.
- ⚠ **과거 데이터**: 북클럽 시트의 기존 '1회성 모임' 행은 **옮기지 않고 그대로 둔다**
  (이전은 신규 접수부터). 필요하면 별도 지시로 수동 이관.
- ⚠ **커피앤바는 결제가 없다** — 선신청 후 개별 연락 구조(카피 근거). 결제 여정과 무관.

## 5. 운영자 결정 대기

1. **새 스프레드시트를 누가 만드나** — 운영자가 만들어 ID 를 주거나, GAS 로 생성 후 공유
2. **커피앤바 URL 슬러그** (`coffee-and-bar` 제안 — URL 정책상 한 번 정하면 고정)
3. **상단부 재현 방식** — 첨부 이미지를 그대로 쓸지, 웹 조판으로 다시 짤지
4. **"평일 19시~24시"** — 신청 폼을 여는 시간인지, 모임 가능 시간대인지
5. **원데이 이전 시점** — 즉시 전환 vs 한동안 두 시트 병행
6. **커피앤바 접수 알림** — 관리자 메일만인지, 카카오 알림톡도 필요한지
